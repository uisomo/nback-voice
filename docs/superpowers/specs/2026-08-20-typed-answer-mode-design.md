# 入力モード(タイプ回答) — 設計

2026-08-20

## 1. 目的

**認識が間違えることが、今いちばん人を脱落させている。** 正しく答えたのに
別の語として文字起こしされ、点が出ない。しかも画面上は普通に動いているので、
壊れていることが分からない。

原因はアプリ自身が認識器を持っていることにある。`expo-speech-recognition` の
結果は**そのまま採点に流れ、訂正の余地がない**。

そこで、回答の入力を**端末のキーボードに預ける**。画面には入力欄を出し、
ユーザーはキーボードのマイクキー(iOSのディクテーション)で喋る。認識するのは
OSで、結果は入力欄のテキストとして現れる。**間違っていれば提出前に直せる。**
これが本設計の全てで、他の変更はここから従属的に出てくる。

副次的に、iOS Safari でもそのまま効く。ディクテーションはSafariの機能ではなく
キーボードの機能なので、RUNBOOK の経路A(トンネル + Safari)でも同じように使える。

音声モードは残す。**既定はタイプ回答**で、音声は設定で選ぶ。

## 2. 用語 — モードは2軸ある

既存の `RoundMode` は**何を採点するか**の軸で、今回足すのは**どうやって
答えるか**の軸。別物なので、1つのenumに畳まない。

| 軸 | 型 | 値 | 意味 |
|---|---|---|---|
| チャネル | `RoundMode` (既存) | `dual` / `question` | 位置を採点するか |
| 入力 | `AnswerInput` (新規) | `voice` / `typed` | 声で答えるか、打って答えるか |

4通り全てが成立する。`question` × `typed` は最も静かな形(グリッドなし・
入力欄だけ)、`dual` × `typed` が既定。

## 3. 採用した方針と、採らなかった方針

**採用: タイプ回答を `Listener` の別実装として作る。**

`RoundRunner` は**タイマーを1つも持たない**。フェーズが閉じてよくなったら
UIが `tick()` を呼ぶ。つまり「フェーズBはいつ閉じてよいか」の答えを差し替え
れば、状態機械は一切変えずに入力方式を変えられる。既存の `Listener` の形が
そのまま使える:

| メソッド | 音声(現行) | タイプ(新規) |
|---|---|---|
| `start()` | マイクを開く | 入力欄を空にして焦点を当て、時計を始める |
| `push(text)` | 認識結果 | `TextInput` の `onChangeText` |
| `settle()` | 最終結果が届いたら解決 | **提出されたら解決** |
| `stop()` | 最終の文字起こし | 入力欄のテキスト |

フェーズBは現在 `max(タイマー, settle())` で閉じる。音声はタイマーを持ち、
タイプは**タイマーを渡さない**ので `settle()` だけで閉じる。これが
「提出駆動」の実装そのものになる。`RoundRunner`・`RoundEngine`・judge・
適応Nのどれも変えなくてよい。

採らなかった案:

- **`AnswerInput` という抽象を新設して `Listener` を置き換える。** 名前は
  正直になるが、`runner.ts` / `fakes.ts` / `GameScreen.tsx` とそれぞれの
  テストに及ぶ改名で、挙動は1ミリも変わらない。`Listener` の doc comment に
  「回答を集めるもの」と書けば足りる。
- **`TypedRoundRunner` を別に作る。** 自由度は最大だが2相の背骨が二重化し、
  以後ラウンドの規則を変えるたびに2箇所直すことになる。

## 4. `src/speech/typed.ts` (新規)

`Listener` を実装する。UIを一切参照しない — テストは画面なしで書ける。

```ts
export class TypedListener implements Listener {
  start(): void          // text = '', submitted = false, 新しい settle を用意
  push(text: string): void
  settle(): Promise<void> // submit() が呼ばれるまで解決しない
  stop(): string          // 現在の text
  sessionEnded(): void    // 何もしない (セッションの概念がない)
  submit(): void          // UIの送信ボタン / return キーが呼ぶ
}
```

- `submit()` は `settle()` の promise を解決する。二重提出は無視する。
- `start()` を待たずに `submit()` が来たら無視する(キーボードの取りこぼし)。
- 空文字のまま提出したら `stop()` は `''` を返し、既存の規則どおり
  **未回答**になる。誤答にはしない。

**回答を求められないステップ**(先頭Nステップ)を誰が扱うかを決めておく。
`TypedListener` はステップの存在を知らないので、ここで判断させない。
**UIが判断する**: `plan.steps[i].recallTarget === null` のステップでは
`settle()` を待たず、通常のフェーズBタイマーだけで `tick()` する。

`RoundRunner.readyToClose()` を賢くする案は採らない。音声モードの
フェーズBの閉じ方まで一緒に変わってしまい、この設計と関係のない挙動変更に
なるため。

## 5. 時間予算と時計

### 5.1 予算

```ts
// src/engine/budget.ts (新規・純関数)
export const DEFAULT_BUDGET_BASE_MS = 4000;

export function answerBudgetMs(answer: string, baseMs: number): number {
  return baseMs + Array.from(answer).length * 1000;
}
```

`answer` は**いま答えるべき問題**(Nステップ前)の `accept[0]`。画面に出て
いない問題の答えなので、時計の長さは答えの字数を漏らす。**これは承知の上で
残す** — 短いか長いかが分かることは、想起の手がかりとして役に立つ。

`Array.from` で数える(コードポイント単位)。基準値は設定で変えられる。

| 答え | 字数 | 予算 (base 4s) |
|---|---|---|
| わん | 2 | 6s |
| キャピタルコール | 8 | 12s |
| 未コールコミットメント | 11 | 15s |

### 5.2 時計の見え方

- フェーズBの開始で走り出す。残り時間を細いバーと秒数で出す。
- 残っている間は緑 `#4caf7d`、0になったら赤 `#e5534b` に変わる。
- **0になってもラウンドは進まない。** 提出駆動は提出駆動のまま。時計は
  締切ではなく的で、超過は記録されるだけ。

これは意図的な非対称:ディクテーションの直しに時間がかかるのは正常なので、
そこを罰すると本設計の目的を自分で壊す。

## 6. 採点 — 時間内は指標であって難易度ではない

`StepSubmission` に足すのは `elapsedMs?: number` **だけ**。予算のほうは
エンジンが自分で出す — そのステップで答えるべき問題は
`plan.steps[recallTarget].question` としてエンジンが既に持っているので、
UIが計算して渡し直す理由がない。基準値は
`new RoundEngine(plan, { budgetBaseMs })` で受ける(既定 4000)。

`AnswerRecord` は `elapsedMs` と `budgetMs` を保持し、`AnswerReview` が
`onTime: boolean | null` を出す。

**`elapsedMs` が無い = 時計が無い = `onTime` は `null`。** 音声モードは
`elapsedMs` を渡さないので、エンジンは入力方式を知らなくてよい。モードの
分岐がエンジンに漏れない。

新しい集計 `onTimeScore: number | null` を `positionScore` / `answerScore` と
並べる。分母は `STIMULI_PER_ROUND`(位置と同じ扱い)。

**`nextN` は触らない。** N は今までどおり正答率だけで上下する。理由は、新しい
信号で難易度を動かすと調整が難しく、外すと適応ループ全体が壊れて感じられる
から。時間内は結果画面に出る目標であって、難易度の入力ではない。

結果画面:

- 集計行に `時間内 nn%` を追加(音声モードでは出さない)。
- 各行に遅れた印。既存の `答え:` 行の並びに `12.4s / 12s` を出す。

## 7. 画面 — レイアウトC・キーボード常時表示

上から: ヘッダ → いま覚える質問 → 時計 → 入力欄 → グリッド → キーボード。

**キーボードは1ラウンドの間ずっと出したまま**にする。ステップごとに出入り
させるとアニメーションが毎回挟まり、秒を数えるゲームの邪魔になる。

寸法の実測(iPhone 15・縦):

```
852pt − 上部インセット59pt − キーボード約340pt = 453pt
  − ヘッダ24 − 質問ブロック70 − 時計20 − 入力欄48 − 余白30 = 約261pt
  → 正方セル 約87pt   (最小タップ目標は44pt)
```

iPhone SE でも約65pt。**グリッドは狭くならない。** ただしキーボードの高さは
機種と、かな/ローマ字で変わるので、セルは `min(幅/3, 高さ/3)` で正方を保ち、
中央寄せにする(伸びた長方形にしない)。

- **質問は読み上げも続ける。** 見る+聞くの両方で入れる。`expo-speech` は権限
  不要で、フェーズAが発話を待って閉じる規則(`readyToClose`)もそのまま生きる。
  ウォームアップのタップによる解錠も引き続き必要。
- 上に出るのは**いま覚える質問**。答える対象(Nステップ前)は**画面に出さない** —
  出した瞬間にN-backではなくなる。
- 入力欄は `autoCorrect` を切る。日本語の自動修正が専門用語を潰す。
- 送信はキーボードの return と、入力欄右の送信ボタンの両方。
- 先頭Nステップは入力欄を無効にし、`まだ答えません` を出す。
- 末尾Nステップは質問欄を空にし、入力欄だけを生かす。

## 8. 保存とマイグレーション

```ts
export interface Settings {
  // ...既存
  answerInput: 'voice' | 'typed';  // 既定 'typed'
  budgetBaseMs: number;            // 既定 4000
}
```

保存済み設定に両キーがなければ既定が入る。**既存のインストールもタイプ回答
になる**(オーナーの端末を含む)。音声で続けたい場合は設定で1回切り替える。
入力方式ごとに分岐したマイグレーションを書くほどの利得がない。

`RoundRecord` に `onTimeScore?: number | null` を足す。省略可なので過去の履歴は
そのまま読める。

## 10. やらないこと

- **課金・アカウント・サブスクリプション。** 入力方式は設定であって権利では
  ない。「有料ユーザーだけ音声」は認証基盤の話で、この設計の外。
- **ビルドの分割。** 音声を落とした商用ビルドは作らない。したがって App Store
  提出時のマイク/音声認識の権限記述は残る。
- **judge を誰の鍵で叩くかの解決。** 商用配布では利用者が自分のAnthropic鍵を
  貼ることはできない。実在する問題だが本設計では扱わない。
- **時間内でNを動かすこと。** 第6節のとおり。
- **入力欄を複数出すこと。** 提出駆動なので、未提出の回答は常に1つしかない。
- **ディクテーションをアプリから起動すること。** iOS に API がない。アプリに
  できるのは入力欄に焦点を当ててキーボードを出すところまで。

## 追記 (2026-08-21): タイプモードのステップは1相になった

上の§3は「`RoundRunner` を一切変えない」ことを取り柄にしていたが、その結果
タイプモードでも**質問(フェーズA)が終わってから入力欄が開く**ようになって
いた。画面では質問が先に出て、入力欄は後から生き返る。実際に遊ぶと、これは
「読んでから答える」ではなく「待たされてから答える」に感じる。

そこで `RoundRunner` に `merged` を足し、フェーズが `'AB'` の1相になるように
した。**2相に分けていた理由は「認識器に合成音声を聞かせない」ことだけ**で、
テキスト欄は何も聞かないので、タイプモードではその理由が最初から無い。

- `merged: true` のとき、ステップの開始で `speak()` と `listener.start()` が
  同時に走る。質問と入力欄と時計が同じ瞬間に出る。
- `readyToClose()` は**両方**を待つ。早く送っても質問は最後まで喋りきる —
  途中で切れた質問はNステップ後に答えられない、というフェーズAの理由は
  そのまま生きている。
- グリッドはステップの間ずっと光ったままになる (暗くするフェーズBが無い)。
- `speaker.stop()` は**ステップを閉じるとき**に呼ぶ。`start()` で呼ぶと、
  ウォームアップのタップが出した unlock 発話を打ち消して iOS が丸ごと無音に
  なる。
- 回答窓が質問の読み上げ中から開くので、時間予算の base にフェーズAの長さを
  足す (`GameScreen` の `budgetBaseMs`)。足さないと、全ての回答が黙って
  「遅い」判定になる。

音声モードは2相のまま。§3の表と「提出駆動」の話はどちらの形でも変わらない。
